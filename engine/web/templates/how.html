How the engine runs

One web service, five background worker pools, two scheduled jobs and one Postgres database, defined in render.yaml. Workers pull jobs from Postgres; people decide at the gates in this dashboard.

Web service

Dashboard, gate decisions, tutor endpoint, downloads, JSON API. Calls the orchestrator after every human decision.

Scheduled jobs

Quarterly: Lightcast refresh for every live Program.

Every 10 minutes: housekeeping (requeue jobs left by a restarted worker; nudge Programs forward).

The control loop

  1. A Program is created from a Task Order brief: target occupation, credential, source pack.
  2. The orchestrator inspects the Program's records and gates and enqueues the next job (idempotent: each job has a unique key per Program).
  3. A worker in the right pool claims it with SELECT ... FOR UPDATE SKIP LOCKED, runs it, writes the record, and calls the orchestrator again.
  4. Where the proposal puts a person, the orchestrator opens a gate and waits. A decision in the dashboard moves the Program on, or returns the work with a note that the next draft must apply.
  5. Record writes take a per-Program advisory lock, so many workers and reviewers can act at once without losing an update.

Modes

Lightcast: live when LIGHTCAST_CLIENT_ID and LIGHTCAST_CLIENT_SECRET are set (Open Skills, free). Set LIGHTCAST_LICENSED_PRODUCTS=true with UMGC's or Magic's license to call LOT, Job Postings Analytics and Career Pathways. Otherwise mock: every ID and demand figure starts with MOCK.

Claude: live when ANTHROPIC_API_KEY is set (model in ANTHROPIC_MODEL). Otherwise template drafting, labeled as such in every provenance record.
